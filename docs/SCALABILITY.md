# Scalability

What it takes to replace every demo source with a real one, and what it takes to
run this for an actual state.

This document is deliberately unflattering about the current build. The system as
committed is a working demonstration on a laptop: 74 point locations, one process,
a SQLite file, a modelled weather series and a model trained on synthetic labels.
Each of those is a real limit, and each has a known replacement with a known cost.
Nothing below is aspirational architecture — every seam named here exists in the
code today.

## The one design decision that makes this possible

Every external dependency enters the system through exactly one module, and every
value carries a provenance label. That is the whole trick.

```
        real world                    the seam                  everything else
────────────────────────────  ─────────────────────────  ─────────────────────────
rainfall, temperature, humidity ─► weather_service.py ─┐
DEM, land cover, NDVI, soil     ─► terrain_service.py ─┤
landslide inventory             ─► seed.py / events    ├─► preprocess.py (16 features)
telemetry                       ─► sensor_simulator.py ─┤        │
the trained model               ─► ml/  (features.py)  ─┘        ▼
                                                        risk_engine ─► API ─► UI
```

Downstream of `preprocess.py` nothing knows or cares where a number came from. A
score, a forecast, an alert, an explanation and a map disc are all computed from
sixteen named features, and the data-mode label rides along beside them. So
replacing a source is a change to one module plus a change to what the label says
— never a change to the risk engine, the API contract or the frontend.

That claim is worth testing rather than trusting, and it is testable: `LIVE` weather
already works this way. Setting `USE_LIVE_WEATHER=true` swaps a modelled series for
Open-Meteo observations, and the only thing that changes anywhere else in the system
is that responses start saying `LIVE`.

## Replacing the data, source by source

In descending order of how much the substitution buys you.

### 1 · Labels — the one that actually matters

**Today.** Labels are Bernoulli draws from the documented slope-stability model in
`ml/physics.py`, generated by `ml/data/generate_dataset.py`. The model therefore
learns that physical model, not the observed landslide record.

**Replace with.** The GSI National Landslide Susceptibility Mapping inventory, the
NRSC landslide atlas, or a state DDMA's own incident register. Join each recorded
failure to the rainfall that preceded it and the terrain it happened on.

**How.** Write a loader that returns a DataFrame with the sixteen feature columns
plus `landslide_occurred` and `region_code`, and point `train_model.py` at it
instead of the generator. `--data` already takes a path. Nothing else changes:
`preprocess.py`, the split logic, the metrics, the calibration table, the model
card and the whole serving path are indifferent to where the frame came from.

**What it costs.** Weeks of data work, not hours — and it is honest to say that most
of the effort in making this real lives here. Three specific problems arrive with
real labels. Negatives are unlabelled rather than absent: an inventory records
failures, not the hours nothing happened, so you must construct negatives (usually
by sampling space-time cells with no recorded event) and accept that some of them
are unrecorded positives. Reporting is biased towards roads, settlements and
fatalities, so the inventory undersamples remote slopes; a model trained naively
learns where people report, not where slopes fail. And the class balance will be far
worse than the 10% in the synthetic set — expect fractions of a percent, which makes
PR AUC and calibration the only metrics worth reading.

**What to expect.** The honest metrics will drop. A cross-validated ROC AUC in the
0.75–0.85 range against a real inventory would be a good result, and it would mean
something the current 0.8254 does not.

### 2 · Weather

**Today.** `ml/hydrology.py` generates a year-long hourly series per region, seeded
from the region code — deterministic, physically consistent, labelled `DEMO`.
Setting `USE_LIVE_WEATHER=true` fetches Open-Meteo instead and labels rows `LIVE`,
falling back to `DEMO` with a stated reason if the call fails.

**Replace with.** IMD gridded rainfall (0.25° daily, 0.5° hourly products) for
observations and IMD's district forecasts for the forward window; AWS/ARG station
data where a state has its own network; GPM IMERG for near-real-time satellite
rainfall where gauges are sparse.

**How.** `weather_service.py` is the only module that knows where weather comes
from. It already has the shape you need: `current()`, `forecast_hours()`,
`hourly_window()`, and a `provider_status()` that reports what is actually
answering. Add a provider branch beside `_fetch_live` and the label follows
automatically.

**What it costs.** Modest engineering, real operational work. The interesting part is
not fetching — it is that real gauge data has gaps, and the five nested rainfall
windows must stay nested through them. Interpolate before featurising, not after.
`preprocess.py` will enforce monotonicity regardless, but silently, and a silently
repaired gap is a wrong feature.

**One thing to keep.** Store fetched observations in `weather_data`. The table exists
and is indexed for it, and the current build does not write to it — the in-process
series is cheaper and cannot drift between "now" and "+6 h". Real ingestion should
persist, because you will want to retrain on your own history.

### 3 · Terrain

**Today.** Approximate published values per district in
`ml/data/regions_seed.py`, projected by `terrain_service.py`, labelled `DEMO`. The
service publishes its own replacement plan through `GET`-able
`source_catalogue()` — six layers, each with what the demo uses and what production
should use.

| Layer | Demo | Production |
| --- | --- | --- |
| Elevation, slope | Approximate published values per district | Cartosat-1 / SRTM 30 m DEM via Bhuvan or USGS EarthExplorer |
| Land cover | One representative class per region | NRSC / Bhuvan LULC 50k, or ESA WorldCover 10 m |
| Vegetation index | Class-typical NDVI with a per-region offset | Sentinel-2 or Landsat-8 NDVI composite, 16-day cadence |
| Soil | One representative class per region | NBSS&LUP soil map, or SoilGrids 250 m |
| Hydrography | Deterministic per-region distance | Survey of India drainage / HydroSHEDS |
| Inventory | Documented plus modelled events | GSI National Landslide Susceptibility Mapping |

**How.** Compute slope, aspect, curvature and local relief from the DEM once with
GDAL or `richdem`, zonal-summarise per unit, write the results into `terrain_data`,
and delete the fallback. This is a batch job, not a service: terrain changes on the
timescale of a DEM refresh.

**What it costs.** A day or two of GIS work per state, plus storage for the rasters.
It is the cheapest substitution on this list with the largest visible effect,
because slope and its derivatives are where the model's terrain signal actually
comes from.

**The resolution question is the real one.** A 30 m DEM zonal-averaged over a
district produces a number that describes no slope in it. This matters more than the
data source, and it is the subject of the next section.

### 4 · Telemetry

**Today.** There is no hardware anywhere in this project. `sensor_simulator.py`
produces five instrument types per region, every reading labelled `SIMULATED`, each
one documenting the real instrument it stands in for.

**Replace with.** Whatever a state actually has — tipping-bucket rain gauges,
capacitance soil-moisture probes, tiltmeters, geophones, piezometers — over MQTT,
LoRaWAN or a vendor API.

**How.** `sensor_simulator.py` becomes an ingestion adapter. `simulated_sensor_data`
already has the right columns (`sensor_code`, `sensor_type`, `reading`, `unit`,
`status`, `recorded_at`, `data_mode`); rename the table, flip `data_mode` to `LIVE`,
and the risk engine, the sensor page and the history endpoint keep working.

**What it costs.** This is the only item on the list that stops being a software
project. Everything above can be done by one developer with public data.

## From 74 points to a grid

The substitution nobody asks about in a demo, and the one that decides whether this
is useful.

Today a region is a **point** with representative terrain. "Wayanad is HIGH" means
the modelled Wayanad profile is HIGH — not that any particular slope in the district
is. For triage across a state that is defensible; for telling a specific village to
move, it is not.

The operational unit should be a grid cell or a slope unit, not a district:

| Unit | Cells for Kerala (~39 000 km²) | Cells for India's hill states (~500 000 km²) |
| --- | --- | --- |
| District point (today) | 14 | ~120 |
| 5 km grid | ~1 600 | ~20 000 |
| 1 km grid | ~39 000 | ~500 000 |
| 100 m grid | ~3.9 M | ~50 M |
| Slope units (hydrological) | ~50 000 | ~600 000 |

Nothing in the feature contract changes — a cell has slope, soil, rainfall and a
history just as a district does. Three things elsewhere do.

**`regions` stops being a point table.** Add the polygon geometry PostGIS is already
loaded for, keep the centroid for the marker, and index on the geometry rather than
the code.

**Scoring stops being interactive.** All 74 regions currently score inside one
request; 39 000 cannot. The pattern is the same one this build already uses for
persistence — compute on a schedule, serve from storage. `risk_predictions` is
already shaped for it, and `v_current_risk` already answers "latest score per unit"
in one indexed query.

**The map stops sending points.** 39 000 discs will not render. Serve vector tiles or
a server-side aggregation by zoom level, and drop to individual units only when the
viewport is small enough to warrant it.

The honest summary: going from 74 points to a 1 km grid is roughly a 500× increase in
inference volume and a change from request-time to scheduled scoring. It is a known
piece of engineering, not a research problem — but it is a rewrite of the scoring
loop, not a configuration change, and this document should not pretend otherwise.

## Compute, measured rather than guessed

What the current build actually does, so the arithmetic below has a floor under it.

A full risk-map refresh scores every region in one batched call — `predict_batch`
stacks the matrix and runs five members over it once, which is why 74 regions cost
far less than 74 single predictions. Explanations are skipped in batch on purpose;
only the region an officer selected gets one. Weather series are built once per
region (~60 ms, ~0.3 MB) and cached in process. Scores are cached on
(region, scenario version, hour, model path), and persisted only when the band
changed, the score moved more than 2 points, the scenario changed, or the stored row
aged past `max(60, REFRESH_SECONDS)` seconds.

Scaling that shape up:

| Units | Inference | Storage per scoring pass | Realistic cadence |
| --- | --- | --- | --- |
| 74 | Milliseconds, in-request | ~74 rows | On demand |
| 1 600 (5 km, one state) | Under a second, batched | ~1 600 rows | Every 15 min |
| 39 000 (1 km, one state) | Seconds on one core | ~39 000 rows | Hourly |
| 500 000 (1 km, all hill states) | Minutes, embarrassingly parallel | ~500 000 rows | Hourly, sharded |

Gradient-boosted trees are cheap and the work partitions perfectly by region, so
inference is not the constraint at any of these sizes. The constraints are the
rainfall ingestion pipeline and the write volume — at 500 000 units hourly, the
conditional-persist rule stops being an optimisation and becomes the only thing
keeping the table a sensible size.

## Where the current build would break first

In the order you would hit them.

**The scenario switch is process-level.** `ScenarioState` lives in one process behind
a `threading.Lock`. Run `uvicorn --workers 4` today and workers disagree about which
scenario is active. This is documented in `ARCHITECTURE.md` and is fine for a
single-process demo; it is the first thing to move to Redis or a database row before
any horizontal scaling.

**The risk-engine and weather caches are per-process.** Same reason, same fix. Both
are correct but unshared, so four workers do four times the work and can serve four
different answers within one refresh window.

**Uploads go to the local filesystem.** `citizen_reports.image_path` is a path under
`UPLOAD_DIR`. Two instances behind a load balancer will not see each other's images.
Move to S3-compatible object storage and keep the key in the same column.

**SQLite is a single-writer database.** Fine for a laptop, wrong for concurrent
officers. Switch to the PostgreSQL configuration that already ships in
`docker-compose.yml` — one environment variable — and the code path is unchanged
because SQLAlchemy handles both.

**Scoring happens inside the request.** Above a few hundred units, a dashboard load
that scores everything becomes a timeout. Move to a scheduled job.

**JWTs cannot be revoked.** `security.py` issues stateless HS256 tokens with an
expiry and no revocation list, and the demo secret is in `config.py`. Before anything
reachable: real secret, shorter expiry, and either a revocation store or refresh
tokens.

**`POST /alerts/sweep` is anonymously callable.** It is the scheduled-scoring entry
point and it takes no authentication today. Whatever runs it on a schedule should be
the only thing able to.

## A deployment shape that would work for one state

Not a target architecture for its own sake — the smallest change from what exists
that a state DDMA could actually run.

```
                      ┌─────────────────────────────────────┐
   IMD / AWS gauges ──►│  ingest worker   (hourly)          │
   GPM IMERG        ──►│  writes weather_data               │
                      └──────────────┬──────────────────────┘
                                     ▼
                      ┌─────────────────────────────────────┐
   terrain_data ──────►│  scoring worker  (hourly, sharded) │
   model.pkl    ──────►│  risk_predictions, risk_forecasts, │
                      │  alerts                             │
                      └──────────────┬──────────────────────┘
                                     ▼
   ┌──────────────┐    ┌─────────────────────────────────────┐
   │ PostgreSQL   │◄───┤  FastAPI (N stateless replicas)     │
   │ + PostGIS    │    │  reads stored scores, serves tiles  │
   └──────────────┘    └──────────────┬──────────────────────┘
   ┌──────────────┐                   │
   │ Redis        │◄──────────────────┤  scenario state, caches
   └──────────────┘                   │
   ┌──────────────┐                   ▼
   │ Object store │◄───────  React app / mobile / SMS gateway
   └──────────────┘          report images
```

Five changes from the current build, in dependency order. Point `DATABASE_URL` at the
PostgreSQL service that already ships in `docker-compose.yml`. Move `ScenarioState`
and the risk cache into Redis. Move the scoring loop out of the request path into a
worker on a schedule, authenticated. Move uploads to object storage. Then, and only
then, run more than one API replica.

None of those touches the ML package, the feature contract, the API shape or the
frontend. That is the return on having put every external dependency behind a single
module.

## What would still be missing

A platform that warns people needs more than a model, and it is worth being explicit
about what this build does not attempt.

**Delivery.** Alerts land on a dashboard. Real warning means SMS to registered
numbers, Cell Broadcast or CAP feeds to NDMA's Sachet, sirens, and an escalation
ladder with acknowledgement timeouts. The alert workflow here — new, acknowledged, in
progress, resolved, with illegal transitions refused — is the state machine that
would sit underneath that, but the last mile is absent.

**Thresholds per region.** `ALERT_HIGH_THRESHOLD` and `ALERT_CRITICAL_THRESHOLD` are
global (60 and 80, from the brief). Real thresholds vary by terrain and by what is
exposed downslope: the same score above a highway and above an empty valley do not
warrant the same response.

**Exposure and consequence.** `population_exposed` is carried per region and reported,
but risk is scored on hazard alone. Operational prioritisation needs hazard ×
exposure × vulnerability, which is a different model and a different data problem.

**Verification.** Nothing closes the loop. An operational system records whether each
warning was followed by a failure and feeds that back — which is both how thresholds
get calibrated and the only way to earn trust after a false alarm.

**Non-rainfall triggers.** No earthquake, reservoir drawdown, blasting or excavation
term exists, and each of those has caused failures that this model would have scored
as low risk.

**Audit and accountability.** Notes are stamped with who wrote them and when, and
that is the extent of it. A system whose output can move people needs a full audit
trail, retention rules, and an answer to "who decided, on what evidence, at what
time".

## What to do first

If someone picked this up tomorrow with a month, the order is not the order this
document is written in:

1. **PostgreSQL and scheduled scoring.** Removes the two limits that block everything
   else, and neither is difficult.
2. **A real DEM for one state.** Cheapest substitution, largest visible improvement,
   and it makes the terrain features mean something.
3. **Real rainfall for that state.** Turns the platform from a demonstration into
   something that describes today.
4. **A real inventory, and retrain.** Hardest and slowest, and the only one that
   makes the predictions claims about the world rather than about `ml/physics.py`.
5. **Then delivery.** Not before step 4 — a warning channel carrying unvalidated
   predictions is worse than no channel, because it spends trust it has not earned.

Steps 1 to 3 are a few weeks of work by one person against public data. Step 4 is the
real project.
